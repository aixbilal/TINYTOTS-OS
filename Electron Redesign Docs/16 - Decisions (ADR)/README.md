## Purpose

Defines the ADR system, lifecycle, status model, and how decisions relate to the rest of the documentation.

## ADR Purpose

Architecture Decision Records capture decisions that have meaningful technical consequences.

An ADR should answer:

```text
Problem
   ↓
Options
   ↓
Decision
   ↓
Reasoning
   ↓
Consequences
   ↓
Status
```

## ADR Status

Use explicit statuses such as:

- Proposed
- Accepted
- Superseded
- Deprecated
- Rejected

Do not mark a decision Accepted unless the project evidence supports that status.

## Source Discipline

The redesign specification defines intended future-state requirements.

The verified repository establishes current implementation.

Where decision rationale is not established by either source:

`TODO — decision rationale not established in available sources.`

## ADR Relationship

ADRs explain **why** important decisions exist.

Architecture and implementation documents explain **what** the resulting system is and **how** it works.
