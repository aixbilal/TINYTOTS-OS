### Finding K1-SEC-1 (build-time bake-in) — **must be closed at K.2**
`@opennextjs/cloudflare` `compileEnvFiles` (`dist/cli/build/open-next/compile-env-files.js` → `extractProjectEnvVars`) reads **`.env`, `.env.{mode}`, `.env.local`, `.env.{mode}.local` files** at `build:cf` time and writes every key/value into `.open-next/cloudflare/next-env.mjs` as **plaintext**, which is then bundled into `worker.js`. Confirmed: with real `.env.local` present, `SUPABASE_SERVICE_ROLE_KEY`, `GROQ_API_KEY`, `WHATSAPP_*`, `META_*`, `UPSTASH_*` are all embedded verbatim.

Runtime precedence (`cloudflare-templates/init.js` → `populateProcessEnv`): Cloudflare platform `env` (dashboard Secrets / `vars`) is copied into `process.env` **first and unconditionally**; the baked `next-env.mjs` values are applied only with `??=` (fallback). So dashboard Secrets **functionally override** the baked values — but the baked plaintext still physically ships inside the deployed Worker script and is readable by anyone with dashboard/script access.

Mitigations:
- `.open-next/` is git-ignored → **nothing leaks into the repo or git history.** Exposure risk is entirely at **K.2 deploy time**.
- **K.2 REMOTE ACTION REQUIRED:** run the Cloudflare production build with **no server secrets in any `.env*` file** on the build host (keep only `NEXT_PUBLIC_*` + non-secret config, e.g. via a committed `.env.production` of public values and an absent/sanitised `.env.local` in CI), and supply every `SERVER_RUNTIME_SECRET` via `wrangler secret put` / dashboard encrypted Secrets. Then verify the deployed bundle's `next-env.mjs` contains only public values.

## 13. Chosen cache architecture — and WHY

**Answer to the batch's exact question:** *TinyTots does **not** require time-based ISR infrastructure in production.* Business-critical Supabase content is served **dynamically**; genuinely-static content stays as **prerendered static assets**.

**Option A — selective dynamic SSR + static-assets incremental cache. No R2, no Queue, no KV, no D1, no Durable Objects.**

Evidence:
1. The OpenNext `incrementalCache: static-assets` override is **read-only** — it silently ignores `export const revalidate` and `unstable_cache` writes (no writable store, no background regeneration). `open-next.config.ts`'s own comment already acknowledges "ISR revalidation isn't relied on." So the pre-change `revalidate` exports were **already dead on Cloudflare** — pages would have frozen at the last deploy, which is a silent regression versus the current Vercel behaviour.
2. The codebase has **zero** `revalidateTag` / `revalidatePath` / `unstable_cache` invalidation calls → there is no on-demand-invalidation design to preserve, so a tag-cache / queue is not warranted.
3. The commerce-critical browse/search path (`/products` + all catalog `/api/*`) is **already `force-dynamic`** and stays live regardless.
4. Checkout re-fetches authoritative price/stock server-side (see §20) → a momentarily stale PDP display can never produce a mispriced order.
5. Least complexity, zero added Cloudflare resources, zero recurring cost — matches the brief's "smallest correct architecture."

**Applied in K.1:** 7 Supabase-backed storefront pages converted `revalidate → force-dynamic` (homepage, PDP, collections index + `[slug]`, sale, blog index + `[slug]`). Verified in the build output as `ƒ (Dynamic)` and in the workerd smoke as HTTP 200.

**Left as SSG (redeploy- or K.2-refreshed):** `help`, `help/[slug]`, `our-story`, `privacy-policy`, `terms`, `shipping-returns` — legal/policy/marketing copy, deliberately-rare edits, and keeping them prerendered is the best choice for Free-tier CPU. If the owner later wants live edits to these without a redeploy, convert them to `force-dynamic` too (same one-line change) — that is the only remaining cache decision and it needs no infrastructure.

**Trade-off flagged for K.2 staging:** more pages now render per-request → higher Worker CPU per hit. This **cannot be validated locally** (workerd ≠ production isolate limits). K.0 already concluded the Free **CPU** ceiling is marginal and recommended the **Paid** plan; K.1 does not change that conclusion. Free-tier **size** eligibility is unaffected (see §15/§30).

## 20. Checkout architecture
Client cart → `POST /api/checkout` (rate-limited) → server re-fetches variants, recomputes totals in **PKR**, validates stock, writes order + decrements stock atomically, returns `order_number` → `/order-confirmation/[order_number]` (dynamic). Payment method persisted as COD; other methods gated "Coming Soon". No third-party payment SDK, no currency conversion, no ZIP/state logic.
