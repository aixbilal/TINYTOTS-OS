# TinyTots Web Design — Design Principles

## 1. The Core Rule

> **Premium is a system, not a decoration.**

A premium result comes from consistency across typography, spacing, photography, interaction, performance, and content hierarchy.

## 2. Principle: Editorial Over Template

The public website should feel composed like a fashion editorial.

Use:

- large imagery
- intentional cropping
- asymmetry where useful
- varied section rhythm
- controlled text density

Avoid:

- repetitive card grids as the only composition
- identical section structures everywhere
- generic ecommerce blocks

## 3. Principle: Restraint Over Spectacle

Effects are allowed, but they must earn their place.

Every proposed effect must answer:

1. What does it communicate?
2. What does it improve?
3. Why is static UI insufficient?
4. What is the performance cost?
5. What happens with reduced motion?

If these cannot be answered, reject the effect.

## 4. Principle: One Design Language

All components must feel related.

The system must define:

- typography
- color
- spacing
- radius
- elevation
- motion
- states

No page may invent a new visual language without an explicit design-system decision.

## 5. Principle: Photography First

For a fashion brand, photography is not filler.

UI should support the image rather than compete with it.

## 6. Principle: Typography Creates Character

Typography must establish:

- hierarchy
- confidence
- elegance
- readability

Decorative fonts should never reduce usability.

## 7. Principle: Whitespace Has Meaning

Whitespace may be used to:

- separate concepts
- emphasize products
- create calm
- increase perceived quality
- create visual rhythm

Empty space should be intentional.

## 8. Principle: Motion Preserves Continuity

When something moves, the user should understand where it came from and where it went.

Avoid random entrance animations.

Prefer:

- shared-element-like continuity
- directional transitions
- subtle scale
- opacity
- masking
- controlled parallax

## 9. Principle: Tactile Interaction

Buttons, controls, cards, and navigation should have a sense of physical response.

Tactility should come from:

- timing
- easing
- scale
- position
- opacity
- cursor feedback

not excessive shadows or artificial 3D effects.

## 10. Principle: User and Admin Are Different

### User

Optimize for:

- emotion
- discovery
- storytelling
- confidence
- purchase

### Admin

Optimize for:

- speed
- scanning
- accuracy
- control
- data density

Shared system, different experience.

## 11. Principle: Progressive Disclosure

Do not show every possible action at once.

Primary actions should be obvious.

Secondary actions should appear when relevant.

Advanced actions can live behind contextual menus.

## 12. Principle: Consistency Beats Novelty

A slightly less exciting component that works everywhere is better than a spectacular component used once.

## 13. Principle: Accessibility Is Not Optional

Accessibility is part of the design definition.

Do not solve accessibility after the visual design.

## 14. Principle: Performance Is a Luxury Feature

Fast interaction increases perceived quality.

Reject:

- oversized unoptimized images
- unnecessary animation libraries
- uncontrolled WebGL
- excessive DOM effects
- animation that blocks interaction

## 15. Principle: Build for Change

The system should support future:

- collections
- campaigns
- products
- editorial stories
- content
- admin modules

without redesigning the foundation.

## 16. Principle: Preserve Business Reality

Do not invent UI around features that do not exist.

Repository and business evidence outrank assumptions.

## 17. Principle: No Copying

Reference brands are sources of principles, not visual templates.

TinyTots must emerge as its own identity.

## 18. Principle: Every Rule Has an Exception Path

If a design rule must be broken, document:

- what is being broken
- why
- where
- duration
- expected impact
- whether the exception should become a new reusable pattern

Undocumented exceptions become inconsistency.

## 19. Design Decision Test

Before approving a major feature, evaluate:

| Criterion | Question |
|---|---|
| Brand | Does it strengthen TinyTots? |
| UX | Does it improve the task? |
| Hierarchy | Does it clarify attention? |
| Accessibility | Can everyone use it? |
| Performance | Is the cost justified? |
| Reuse | Can the pattern be systematized? |
| Maintainability | Can developers maintain it? |
| AI clarity | Can an implementation agent understand it? |

A feature should not be approved solely because it looks impressive.
