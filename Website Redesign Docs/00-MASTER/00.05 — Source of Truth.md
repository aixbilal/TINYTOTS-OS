# TinyTots Web Design — Source of Truth

## 1. Purpose

This document defines which information has authority during the redesign.

The project uses multiple sources:

- existing repository
- existing screenshots
- design documentation
- generated visual references
- AI reports
- implementation changes

These sources do not have equal authority.

## 2. Authority Hierarchy

When sources conflict, use this order:

### Level 1 — Business Truth

Confirmed business requirements and constraints.

### Level 2 — Production Repository

The actual implementation is the authority for:

- existing routes
- existing files
- current dependencies
- actual component relationships
- API contracts
- data behavior

### Level 3 — Approved Design Documentation

The approved design tree is the authority for the new intended experience.

### Level 4 — Approved Design References

Moodboards and visual references support the design system but do not override written rules.

### Level 5 — AI Analysis

AI reports are evidence and recommendations.

They are not automatically authoritative.

### Level 6 — Inspiration

External brands and UI libraries are inspiration only.

## 3. Current-State vs Future-State

Every document must distinguish:

`CURRENT`

What exists now.

`TARGET`

What should exist after redesign.

`DECISION`

What was intentionally chosen.

`ASSUMPTION`

What is not yet verified.

## 4. Screenshot Authority

Screenshots are authoritative for:

- observable visual appearance
- visible navigation
- visible page hierarchy
- visible component behavior

Screenshots are not authoritative for:

- hidden routes
- backend architecture
- data models
- component file names
- implementation dependencies

Those require repository verification.

## 5. Repository Authority

When implementing a change, the coding agent must inspect the repository before making assumptions about:

- route location
- component ownership
- styles
- shared dependencies
- asset usage
- API calls

## 6. Documentation Authority

Once a design document is marked:

`status: approved`

it becomes the design authority unless a later document explicitly supersedes it.

## 7. Superseding Rules

A new decision must:

1. reference the old decision
2. explain why it changed
3. state what replaces it
4. identify affected documents
5. update status where applicable

Do not silently rewrite a decision.

## 8. AI Evidence Labels

All AI-generated repository reports must classify claims:

- `VERIFIED`
- `OBSERVED`
- `INFERRED`
- `PROPOSED`
- `UNKNOWN`

Unknown is preferable to guessing.

## 9. Obsidian Role

Obsidian is the human-readable knowledge layer.

It should contain:

- design decisions
- specifications
- references
- relationships
- project status
- implementation rules

It should remain navigable without requiring an AI agent.

## 10. GitHub Role

GitHub is the source of truth for actual implementation.

No documentation should claim that code exists solely because an AI proposed it.

## 11. AI Working Context

AI agents may use:

- relevant documentation
- targeted repository reports
- exact source files
- implementation tasks

They should not be required to rediscover the entire project for every task.

## 12. Conflict Handling

If an AI discovers that implementation conflicts with documentation:

1. stop the affected change
2. report the conflict
3. identify the authoritative source
4. propose resolution
5. update documentation if the decision changes
6. then implement

## 13. Final Rule

> **Never replace verified information with a plausible guess.**

This rule applies to design, architecture, routes, files, business behavior, and implementation.
