# TinyTots Web Design — Documentation Standards

## 1. Purpose

These standards ensure every document remains understandable to:

- humans
- designers
- developers
- AI coding agents
- future maintainers

## 2. File Naming

Use:

```text
NN.SS — Descriptive Name.md
```

Where:

- `NN` = major section
- `SS` = document sequence

Example:

`08.01 — Homepage.md`

## 3. Frontmatter

Every Markdown document must begin with YAML frontmatter:

```yaml
---
id: 08.01
title: Homepage
status: draft
phase: 08
ai_critical: true
last_updated: YYYY-MM-DD
---
```

Optional fields may include:

```yaml
owner:
depends_on:
supersedes:
related:
source:
```

## 4. Status Values

Use only:

`draft`

`in-review`

`approved`

`deprecated`

`blocked`

`needs-verification`

## 5. Evidence Types

Use explicit labels:

### OBSERVED

Visible in screenshots or current UI.

### VERIFIED

Confirmed in repository or authoritative project data.

### PROPOSED

A future design decision.

### ASSUMPTION

Temporary assumption awaiting verification.

### UNKNOWN

Information not currently available.

## 6. Document Structure

Major design documents should normally use:

```text
# Title

## Purpose

## Current State

## Target State

## Requirements

## Rules

## States

## Responsive Behavior

## Motion

## Accessibility

## Performance

## Implementation Notes

## Acceptance Criteria

## Dependencies

## Related Documents
```

Not every document requires every section, but important decisions must not be hidden in prose.

## 7. Requirements

Use testable language.

Bad:

> The page should be elegant.

Good:

> The hero must use one dominant image, one primary headline, and no more than one primary CTA on the initial viewport.

## 8. Rules

Rules should be explicit and measurable where possible.

Examples:

- maximum text width
- spacing values
- animation duration
- allowed colors
- component states
- breakpoint behavior

## 9. Decision Records

Major decisions should state:

```text
Decision
Reason
Alternatives considered
Trade-offs
Impact
Affected documents
```

## 10. No Ambiguous Language

Avoid:

- nice
- cool
- premium-looking
- modern
- smooth
- beautiful

unless they are followed by concrete design criteria.

## 11. Code References

When referring to implementation:

Always include exact path when known.

Example:

```text
app/page.tsx
components/product/ProductCard.tsx
```

Do not invent file paths.

If unknown:

`PATH REQUIRES REPOSITORY VERIFICATION`

## 12. External References

External references must explain:

- what is being referenced
- what principle is useful
- what TinyTots is adopting
- what TinyTots is explicitly not copying

## 13. AI Readability

Documents should be:

- modular
- explicit
- internally consistent
- linkable
- machine-readable
- free from contradictory duplicate rules

## 14. Obsidian Linking

Use wiki links where useful:

```text
[[02.01 — Color System]]
[[04.02 — Timing & Easing]]
[[08.01 — Homepage]]
```

## 15. Tables

Use tables for:

- tokens
- states
- comparisons
- acceptance criteria
- component variants

Avoid using tables for long narrative text.

## 16. Code Blocks

Use code blocks only for:

- configuration
- tokens
- schemas
- example structures
- implementation patterns

Never use code blocks to hide ordinary prose.

## 17. Screenshots and References

Each visual reference should have:

- source
- purpose
- observed principle
- TinyTots interpretation
- approval status

## 18. Versioning

If a major design decision changes:

- do not silently replace historical reasoning
- document the change
- identify affected documents
- update the source-of-truth reference

## 19. Completeness Standard

A document is complete when another competent designer/developer can act on it without needing to ask:

> "What exactly do you mean?"

## 20. Quality Test

Before marking `approved`, ask:

1. Is the requirement explicit?
2. Is the target behavior clear?
3. Are dependencies known?
4. Are exceptions documented?
5. Can an AI implement it?
6. Can a human review it?
7. Can QA test it?

If not, it remains `in-review` or `needs-verification`.
