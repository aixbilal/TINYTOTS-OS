# TinyTots Three.js Strategy

## Purpose

Three.js is the low-level 3D rendering foundation considered for TinyTots web experiences.

The implementation must remain modular and progressive.

## Responsibilities

Three.js may handle:

- scene creation
- cameras
- lights
- materials
- geometry
- textures
- loaders
- render loop
- post-processing where justified

## Architecture Principle

Do not place an entire 3D application inside a page component.

Preferred conceptual structure:

```text
PAGE
  ↓
3D EXPERIENCE
  ↓
SCENE
  ├── CAMERA
  ├── LIGHTING
  ├── SUBJECT
  ├── ENVIRONMENT
  └── INTERACTION
```

## Asset Loading

Use appropriate asynchronous loading.

Large assets must not block critical HTML/UI.

## GLTF / GLB

For production product/scene assets, compressed and optimized GLTF/GLB workflows should be preferred where appropriate.

Potential optimization techniques:

- geometry compression
- texture compression
- texture resizing
- instancing
- mesh simplification

Exact tools depend on the final asset pipeline.

## Render Loop

Continuous rendering should be avoided when the scene is visually static.

Where practical:

- render on demand
- pause when offscreen
- pause when tab is hidden

## Visibility

Use viewport visibility to determine whether expensive scenes need active rendering.

## Post Processing

Post-processing is optional.

Use only when the visual result justifies:

- additional GPU work
- additional implementation complexity
- compatibility risk

## Shaders

Custom shaders are allowed only when they provide a meaningful visual effect.

Avoid shader complexity for effects achievable with CSS or standard materials.

## Three.js Boundary

Three.js code should not leak unnecessarily into normal UI components.

## Acceptance Criteria

A developer can remove a 3D scene without destabilizing the rest of the page.
