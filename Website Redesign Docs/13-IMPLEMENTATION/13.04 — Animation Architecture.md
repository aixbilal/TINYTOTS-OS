# Animation Architecture

## Purpose

Define a maintainable animation system for the premium TinyTots experience.

## Animation Hierarchy

```text
MICRO INTERACTION
↓
COMPONENT MOTION
↓
SECTION MOTION
↓
PAGE CHOREOGRAPHY
↓
SIGNATURE EXPERIENCE
```

Use the lowest appropriate level.

## Recommended Technology Roles

### CSS

Use for:

- hover
- focus
- simple transitions
- transforms
- opacity
- simple state changes

### Motion Library

Use for:

- React enter/exit
- shared motion primitives
- layout transitions
- component-level choreography

### GSAP

Use only where timeline-level control is genuinely required.

Potential uses:

- complex scroll choreography
- coordinated hero sequences
- advanced editorial timelines

Do not introduce GSAP merely because it is powerful.

## Animation Principles

### Purpose

Every significant animation should answer:

> What does this movement communicate?

### Restraint

The majority of interactions should be subtle.

### Interruptibility

Users should not be trapped inside long animations.

### Performance

Prefer transform and opacity where possible.

Avoid unnecessary layout-triggering animation.

### Accessibility

Respect:

```text
prefers-reduced-motion
```

## Animation Ownership

Animations should have clear ownership.

Avoid several libraries controlling the same element.

## Cleanup

Animations must be cleaned up when components unmount.

Scroll listeners, observers, timelines, and animation contexts must not leak.

## AI Rule

Before adding a new animation dependency, inspect existing dependencies and approved interaction references.
