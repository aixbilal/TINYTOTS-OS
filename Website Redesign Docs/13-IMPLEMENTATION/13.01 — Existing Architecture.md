# Existing Architecture

## Purpose

Define how the redesign must work within the existing TinyTots codebase rather than treating the redesign as a greenfield project.

## Known Architecture

TinyTots currently uses a web application based on:

- Next.js
- React
- TypeScript
- Tailwind CSS / CSS modules where appropriate
- Supabase
- Vercel-oriented deployment
- API routes / server-side integration
- existing customer-facing pages
- existing admin functionality

The repository remains the technical source of truth.

## Architecture Principle

```text
EXISTING FUNCTIONALITY
        +
NEW DESIGN SYSTEM
        +
CONTROLLED REFACTORING
        =
REDESIGNED TINYTOTS
```

Do not rebuild working backend behavior merely to change visual presentation.

## Source-of-Truth Rules

1. Inspect the repository before changing architecture.
2. Preserve working business logic unless redesign explicitly requires change.
3. Do not invent routes, APIs, database fields, or components.
4. Reuse existing data contracts where valid.
5. Identify dead or duplicated code before replacing it.
6. Keep frontend redesign separable from backend changes.

## Required Discovery

Before implementation, document:

- app/router structure
- shared layouts
- existing components
- API routes
- Supabase usage
- authentication
- image handling
- state management
- existing design tokens
- current animation dependencies
- existing 3D dependencies

## Change Classification

Every major change should be classified:

```text
VISUAL ONLY
STRUCTURAL FRONTEND
SHARED SYSTEM
DATA / API
DATABASE
INFRASTRUCTURE
```

Visual-only work should not unnecessarily modify deeper layers.

## AI Implementation Rule

AI coding agents must inspect the relevant files before editing.

The documentation is a design and architecture contract; the repository is the implementation source of truth.
