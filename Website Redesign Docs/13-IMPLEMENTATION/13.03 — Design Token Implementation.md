# Design Token Implementation

## Purpose

Translate the approved visual system into a centralized implementation layer.

## Token Categories

At minimum:

```text
COLOR
TYPOGRAPHY
SPACING
RADIUS
SHADOW
BORDER
MOTION
BREAKPOINT
CONTAINER
Z-INDEX
```

## Token Principle

Components should consume semantic tokens rather than arbitrary values wherever practical.

Prefer:

```text
--color-surface
--color-text
--space-section
--motion-standard
```

over repeated unexplained values.

## Color Architecture

Separate:

```text
RAW PALETTE
↓
SEMANTIC TOKENS
↓
COMPONENT USAGE
```

This makes future brand adjustments safer.

## Typography

Define tokens for:

- display
- heading
- body
- label
- caption
- technical/SKU

Maintain the distinction between editorial and utility typography.

## Spacing

Use a controlled scale.

Avoid page-specific arbitrary spacing unless the composition genuinely requires it.

## Motion Tokens

Define:

- duration
- easing
- delay
- reveal distance
- stagger
- reduced-motion behavior

## Responsive Tokens

Where useful, use fluid values rather than creating many breakpoint-specific overrides.

## Implementation Rule

A token should exist when:

1. it is reused,
2. it represents a brand/system decision,
3. or changing it globally would be valuable.

Do not create tokens for every one-off value.

## AI Rule

Never introduce a new visual value when an existing approved token already represents the intended design.
