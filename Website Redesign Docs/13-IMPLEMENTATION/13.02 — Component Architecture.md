# Component Architecture

## Purpose

Define how the premium redesign should be translated into maintainable React components.

## Component Layers

Use a hierarchy similar to:

```text
APP / ROUTE
    ↓
PAGE COMPOSITION
    ↓
SECTION
    ↓
FEATURE
    ↓
UI PRIMITIVE
```

## Page Components

Pages should primarily compose sections.

Avoid placing large amounts of styling and interaction logic directly inside route files.

## Section Components

Sections represent meaningful page-level experiences:

- hero
- editorial story
- collection
- product showcase
- testimonials
- campaign
- service information

## Feature Components

Feature components own reusable behavior such as:

- product cards
- search
- filters
- cart interactions
- accordions
- carousels
- animated reveals

## UI Primitives

Keep low-level primitives reusable:

- buttons
- links
- inputs
- labels
- icons
- containers
- typography primitives

## Component Rules

### Single Responsibility

A component should have a clear reason to exist.

### Composition Over Duplication

Prefer shared components with controlled variants over copied implementations.

### Variants

Use explicit variants for meaningful visual differences.

Avoid large collections of boolean props that create unpredictable states.

### Data Separation

Separate:

```text
DATA
LOGIC
PRESENTATION
MOTION
```

where practical.

## Animation Boundary

Animation should not be scattered throughout unrelated components.

Prefer reusable motion primitives and page-level choreography.

## 3D Boundary

3D experiences should be isolated from normal UI components.

A 3D component must have a fallback.

## Naming

Names should describe function, not appearance.

Prefer:

```text
ProductCard
CampaignHero
SearchOverlay
```

over:

```text
BlackCard
BigHero
FancySearch
```

## AI Rule

Before creating a component, search the repository for an existing equivalent.

Do not create duplicate components because an existing component is inconvenient.
