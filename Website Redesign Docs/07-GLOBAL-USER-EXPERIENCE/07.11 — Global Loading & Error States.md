# TinyTots Global UX — Loading & Error States

## Purpose

Loading and failure states are part of the premium experience.

A premium interface must remain trustworthy when things go wrong.

## Loading Principles

Do not use a global spinner for every operation.

Prefer contextual loading:

- skeleton
- inline progress
- button processing state
- content placeholder

## Skeletons

Skeletons should approximate the final layout.

Avoid overly animated skeletons.

## Navigation Loading

Navigation should communicate transition without unnecessarily blocking the destination.

## Image Loading

Use:

- appropriate placeholders
- stable dimensions
- progressive loading where appropriate

Avoid layout shifts.

## Search Loading

Show loading state near the result area rather than replacing the entire page.

## Cart Loading

Cart updates should preserve existing information while the change processes.

## Checkout Loading

Payment/order submission requires a stronger state:

```text
PROCESSING
↓
DO NOT SUBMIT AGAIN
```

The UI should prevent accidental duplicate actions.

## Error Categories

### Recoverable

Examples:

- temporary network failure
- failed image
- temporary API issue

Provide retry.

### User-Correctable

Examples:

- invalid form
- unavailable quantity

Explain what to change.

### System-Level

Provide:

- clear explanation
- support path
- recovery option where possible

## 404

The 404 page should offer:

- home
- product discovery
- search

## 500 / Unexpected Failure

Remain calm and concise.

Do not expose technical stack traces.

## Offline / Poor Network

If the application detects connectivity limitations, communicate the state where it affects the user's action.

## Reduced Motion

Loading animation must have a reduced-motion alternative.

## Definition of Done

Every major async operation has a deliberate:

```text
IDLE
→
LOADING
→
SUCCESS
→
ERROR
```

state model where applicable.

No critical flow should depend on an unhandled blank screen or indefinite spinner.
