# TinyTots Design System — Data Display & Admin

## 1. Purpose

This establishes the foundation for the Admin Frontend.

## 2. Density

Admin should be information-dense but not cramped.

## 3. Tables

Tables should support:

- sorting
- filtering
- pagination
- selection
- bulk actions
- status
- row actions

Only capabilities supported by actual data/API behavior should be implemented.

## 4. Column Hierarchy

Important information should appear first.

Secondary metadata should have lower visual emphasis.

## 5. Status

Status should combine:

- text
- color
- optionally icon

Do not communicate critical status by color alone.

## 6. Empty States

Every major data view should define:

- no data
- filtered empty
- loading
- error
- success/updated

## 7. Loading

Prefer:

- skeletons for predictable layouts
- progress indicators for operations
- optimistic feedback only when data consistency permits it

## 8. Filters

Filters should be:

- discoverable
- removable
- persistent where useful
- easy to reset

## 9. Bulk Operations

Bulk actions must clearly communicate:

- selected count
- action
- consequences
- confirmation where destructive

## 10. Dashboard

Dashboard should prioritize actionable information.

Avoid KPI decoration with no operational value.

## 11. Acceptance Criteria

Admin users should be able to scan a data view quickly without relying on decorative styling.
