# TinyTots Motion System — Overview

## Purpose

Motion is part of the TinyTots experience, but it must support the brand rather than compete with it.

The target is:

> cinematic, tactile, restrained, responsive.

The site should never feel like a collection of animation demos.

## Motion Hierarchy

```text
FUNCTIONAL MOTION
    ↓
FEEDBACK MOTION
    ↓
NAVIGATION MOTION
    ↓
EDITORIAL MOTION
    ↓
CAMPAIGN MOTION
    ↓
EXPERIMENTAL / 3D MOTION
```

The lower levels must never compromise the higher levels.

## Core Principles

1. Motion must communicate.
2. Motion must preserve usability.
3. Motion must feel intentional.
4. Motion must respect reduced-motion preferences.
5. Motion must degrade gracefully.
6. Motion must not make the interface feel slow.
7. Every major animation must have a performance justification.

## Motion Personality

Preferred:

- smooth
- quiet
- physical
- elegant
- slightly unexpected
- cinematic

Avoid:

- bouncy
- childish
- constantly moving
- flashy
- random
- game-like

## Motion Budget

Not every element should animate.

A premium page should contain periods of visual stillness.

## Implementation Direction

The implementation should prefer existing project dependencies and lightweight browser APIs before adding large animation libraries.

Possible technologies may include:

- CSS transitions
- CSS keyframes
- IntersectionObserver
- Web Animations API
- Framer Motion / Motion where already available
- GSAP for justified advanced sequences
- Three.js/WebGL only for approved 3D experiences

Do not add a dependency solely because it demonstrates an impressive effect.

## Definition of Done

The motion system is complete when every major interaction has a documented:

- trigger
- animation
- duration
- easing
- exit behavior
- reduced-motion behavior
- performance consideration
