# TinyTots Anti-Patterns & Rejected Directions

## 1. Purpose

This document prevents future AI/design iterations from repeatedly proposing directions that conflict with the approved brand position.

A rejected direction can be revisited only through an explicit design decision.

## 2. Rejected: Childish UI

Examples:

- cartoon buttons
- excessive stickers
- toy-like controls
- primary-color overload
- cartoon illustrations everywhere
- bubbly typography as the primary system

Reason:

TinyTots is for children's fashion, not a toy interface.

## 3. Rejected: Generic Luxury Black-and-Gold

Reason:

Black/gold is an easy shortcut to "luxury" but does not automatically create a distinctive TinyTots identity.

The final palette must be derived from the approved art direction and brand strategy.

## 4. Rejected: Neon/Futuristic Luxury

Avoid:

- neon gradients
- cyberpunk backgrounds
- glowing text
- excessive particles
- futuristic HUD interfaces

Reason:

Conflicts with warmth and children's fashion.

## 5. Rejected: Animation Showcase

Do not fill the site with:

- magnetic buttons everywhere
- constant text scrambling
- excessive cursor effects
- perpetual parallax
- scroll-jacking
- random 3D objects
- unrelated hover tricks

Reason:

Creates novelty rather than brand sophistication.

## 6. Rejected: UI-Library Collage

Do not combine:

- Magic UI effect A
- Vengeance UI effect B
- UIverse button C
- Forge UI card D
- Lore UI interaction E

without a unifying system.

UI libraries are component sources, not the brand.

## 7. Rejected: Excessive Glassmorphism

Avoid making every panel:

- translucent
- blurred
- floating
- glowing

Reason:

Creates visual noise and can harm readability.

## 8. Rejected: Card Everything

Not every content block should become a rounded card.

Use:

- open layouts
- sections
- typography
- imagery
- whitespace

where a card is unnecessary.

## 9. Rejected: Fake Urgency

Avoid:

- fake stock warnings
- artificial countdowns
- manipulative popups
- false scarcity

unless driven by real business data.

## 10. Rejected: Desktop-First Compression

Do not design desktop and then simply stack everything on mobile.

Mobile needs explicit design decisions.

## 11. Rejected: Performance Sacrifice

Reject an effect if it creates disproportionate:

- JavaScript cost
- rendering cost
- image weight
- WebGL cost
- input latency

## 12. Rejected: Copying Competitors

Do not recreate another brand's:

- layout
- typography combination
- color identity
- campaign style
- navigation structure

Use principles, not replicas.

## 13. Rejected: Admin as a Marketing Site

The admin must not become an editorial showcase.

Operational users need speed and clarity.

## 14. Rejected: Admin as an Unbranded SaaS Dashboard

The opposite extreme is also wrong.

Admin should still feel like TinyTots.

## 15. Rejected: Design Without Evidence

Never claim:

- a route exists
- a component exists
- a feature exists
- a backend field exists

unless observed or repository-verified.

## 16. Rejection Rule

When a future design proposal conflicts with this document, it must explicitly state:

```text
CONFLICTING ANTI-PATTERN:
REASON FOR EXCEPTION:
EXPECTED BENEFIT:
RISK:
APPROVAL REQUIRED:
```

No silent exceptions.
