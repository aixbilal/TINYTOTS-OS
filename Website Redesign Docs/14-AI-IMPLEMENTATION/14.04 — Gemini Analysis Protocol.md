# Gemini Analysis Protocol

## Purpose

Define Gemini's role as a high-context analysis and preparation layer before expensive repository implementation work.

## Role

Gemini should be used primarily for:

- repository analysis
- design-document synthesis
- file discovery
- dependency mapping
- implementation planning
- visual/design analysis
- identifying relevant files
- generating concise reports for the implementation agent

## Cost-Efficient Workflow

```text
USER REQUEST
↓
GEMINI ANALYSIS
↓
TARGET FILE MAP
↓
IMPLEMENTATION TASK
↓
CLAUDE CODE
↓
VALIDATION
```

The goal is not to replace repository-level implementation.

## Investigation Output

When asked to investigate a feature, Gemini should identify:

- relevant routes
- relevant components
- relevant hooks
- relevant services
- relevant styles
- relevant assets
- relevant dependencies
- relevant documentation
- likely change surface
- risks

## Exact File Paths

When possible, provide exact repository paths rather than broad categories.

Example:

```text
app/products/page.tsx
components/product/ProductCard.tsx
lib/products.ts
```

Do not invent paths.

## Evidence Classification

Use:

```text
VERIFIED FROM REPOSITORY
INFERRED
REQUIRES VERIFICATION
```

## Design Analysis

Gemini should compare the existing implementation against the applicable design documentation and identify concrete gaps.

Prefer:

```text
CURRENT
→ GAP
→ TARGET
→ FILES
```

over vague aesthetic criticism.

## Handoff Output

The final analysis should be concise enough for Claude Code to consume without unnecessary repository duplication.

Recommended structure:

```text
TASK
CURRENT STATE
TARGET STATE
EXACT FILES
DEPENDENCIES
IMPLEMENTATION NOTES
RISKS
VALIDATION
```

## Critical Rule

Gemini must never fabricate repository details.

If a path cannot be verified, mark it as requiring verification.
