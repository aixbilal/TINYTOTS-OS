# AI Context Protocol

## Purpose

Define how AI agents receive, interpret, preserve, and use TinyTots project context.

The objective is to prevent context loss, duplicated analysis, hallucinated architecture, and inconsistent implementation.

## Source-of-Truth Hierarchy

When sources conflict, use this order:

```text
1. LIVE REPOSITORY
2. DATABASE / ACTUAL APPLICATION DATA
3. APPROVED PROJECT DOCUMENTATION
4. APPROVED DESIGN REFERENCES
5. AI ANALYSIS
6. AI ASSUMPTIONS
```

AI assumptions must never silently override verified project facts.

## Required Context

Before substantial implementation, the agent should understand:

- project purpose
- current repository structure
- relevant route
- relevant components
- existing design system
- data dependencies
- current functionality
- applicable documentation phases
- task acceptance criteria
- known constraints

## Context Loading Strategy

Do not load the entire repository unnecessarily.

Use:

```text
TASK
↓
IDENTIFY RELEVANT DOMAIN
↓
IDENTIFY RELEVANT FILES
↓
READ REQUIRED CONTEXT
↓
IMPLEMENT
```

## Context Preservation

An agent must not:

- restart completed design decisions
- replace approved architecture without reason
- invent missing requirements
- treat temporary code as authoritative
- assume an old component is unused without inspection

## Unknowns

When information is unavailable:

```text
VERIFIED
ASSUMED
UNKNOWN
```

must remain conceptually separate.

Unknown information should be investigated rather than fabricated.

## AI Output Standard

Important implementation decisions should state:

- what was found
- what changed
- why it changed
- what files were affected
- what remains uncertain
- how it was validated
