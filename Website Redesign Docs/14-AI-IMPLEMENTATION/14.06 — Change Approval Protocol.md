# Change Approval Protocol

## Purpose

Prevent uncontrolled AI-driven changes from silently expanding scope or altering important architecture.

## Change Classes

### Class A — Safe Local Change

Examples:

- spacing
- typography
- color token usage
- local styling
- small animation adjustments

Usually implementable within an approved task.

### Class B — Shared System Change

Examples:

- shared components
- global tokens
- navigation
- shared animation primitives
- common layouts

Requires explicit awareness because multiple pages may be affected.

### Class C — Architecture Change

Examples:

- framework changes
- state architecture
- data-flow changes
- dependency replacement
- major component restructuring

Requires explicit approval before implementation.

### Class D — Data / Backend Change

Examples:

- database schema
- API contracts
- authentication
- business logic
- Supabase migrations

Never treat these as incidental frontend changes.

## Approval Principle

```text
LOCAL
→ IMPLEMENT

SHARED
→ REVIEW IMPACT

ARCHITECTURE
→ EXPLICIT APPROVAL

DATA / BACKEND
→ EXPLICIT APPROVAL
```

## Scope Control

AI agents should not expand a task simply because they discover unrelated technical debt.

Record unrelated issues separately.

## Dependency Changes

Before adding a dependency, determine:

- whether an existing dependency already solves the problem
- bundle impact
- maintenance implications
- whether the design actually requires it

## Breaking Changes

Any change that may alter existing user behavior requires explicit review.

## Rollback

Large changes should be implemented in logically separable commits or patches where practical.

## Approval Record

For significant changes record:

```text
CHANGE:
REASON:
IMPACT:
FILES:
DEPENDENCIES:
APPROVED BY:
DATE:
```
